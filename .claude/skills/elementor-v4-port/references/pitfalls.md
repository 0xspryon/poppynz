# Pitfalls (Poppynz V4 harness)

## Data and import
- The importer aborts on any rejected or passed-through CSS. Fix the CSS string; never relax `pz_convert_map`.
- A two-value `gap:<row> <col>` shorthand is never converted (whole declaration dropped to customCss). `row-gap` alone also fails; only `column-gap` alone converts. Fix: `gap:<row>;column-gap:<col>` — the unified `gap` sets both row and column to `<row>`, then the explicit `column-gap` overrides just the column value, giving the same net row/column split as the two-value shorthand. Fixed in `hdr` and the home `services/head` local css.
- `pointer-events` is never converted at all (any value) and Free strips it anyway even if it were customCss, so there is no way to express it through a class or local css in this stack. Fixed by dropping `pointer-events:none` from the decorative `deco` class (its dots sit at `z-index:0` while the real content sits at `z-index:1`, so this has no practical effect on clickability) — named deviation, not a bug.
- `opacity` only converts in percentage form (`opacity:55%`); a 0–1 decimal (`opacity:.55` or `opacity:0.55`) is always left in customCss. Fixed in `deco-d2` and `deco-d5`.
- `flex-grow`/`flex-shrink`/`flex-basis` longhands (alone or combined) are never converted, only the `flex` shorthand (`flex:<grow> <shrink> <basis>`) is. Fixed `dot` (`flex-shrink:0` -> `flex:0 0 auto`) and `hdr-nav` (`flex-grow:1` -> `flex:1 1 auto`).
- `transform:rotate(0)` (no unit) is left whole in `customCss` and aborts the import; `rotate(0deg)` converts fine. Any unitless zero-angle in a `transform` needs an explicit unit. Fixed in `quote`'s `desktop:hover`.
- A per-side `border-top-style` / `border-bottom-style` (or `-left-style` / `-right-style`) longhand is ALWAYS left in `customCss` by the 4.2.4 atomic CSS converter and aborts the import, even with only one side declared. `border-width` per side (e.g. `border-top-width`) and the shared `border-color`/`border-style` (no side prefix) DO convert correctly — so write `border-top-width:1.5px;border-style:solid;border-color:X` instead of `border-top-width:1.5px;border-top-style:solid;border-color:X`. But an UNTOUCHED side is not implicitly 0: with only `border-top-width` (and no `border-left-width`/`border-right-width`/`border-bottom-width`) set, the converter emits a `border-width-v2` prop that leaves those sides unspecified, and Elementor's atomic widget then falls back to the browser default `border-width: medium` (`3px`) on them — combined with the shared `border-style:solid`, this rendered a real (if easy-to-miss) 3px left/right border on `band`, `hdr` and `ftr-bottom`, caught only by measuring `getComputedStyle(...).borderLeftWidth` live rather than by eyeballing a render slice. Always set an explicit `0` on every side you are not giving a real width, e.g. `border-top-width:1.5px;border-left-width:0;border-right-width:0;border-bottom-width:0;border-style:solid;border-color:X`. Confirmed live against staging with `pz_converter()->convert()` before touching `classes.ts`, which is faster than a full pack/push/import cycle per guess. Fixed in `band`, `band-top`, `ftr`, `ftr-bottom`, `hdr`.
- A page saved through the Document API needs `wp_set_current_user(1)`; otherwise `save()` returns false silently.
- Editor edits to copy are overwritten by the next import. Port copy changes back into `content/*.ts` first (diff the stored `_elementor_data` against the artefact).
- Polylang: find pages by slug AND language; the same slug may exist in both languages.
- `import.php`'s header/footer template loop (step 4) never called `pll_set_post_language()` (only the pages loop, step 5, did). Every `elementor-hf` post stayed tagged with the site default language, so the by-title-and-language lookup for the `fr` templates never matched and a fresh duplicate "Site header (fr)"/"Site footer (fr)" post was created on every single import run. Fixed by adding the same `pll_set_post_language( $pid, $t['lang'] )` call used for pages, right after `$pid` is resolved. If you see multiple `elementor-hf` posts with the same title, check `pll_get_post_language()` on each — the stale ones are always tagged with the wrong (default) language and are safe to `wp_delete_post( $id, true )`.
- `foreach ( $el['styles'] ?? [] as $sid => &$style )` in `import.php`'s `pz_fill_styles()` silently never applied ANY local per-element CSS (grid-template-columns overrides, one-off spacing, transforms, video sizing — anything not in a global class) on the entire site: PHP's by-reference `foreach` bound to a `??` fallback expression takes a reference into a temporary copy of the result, not into the real `$el['styles']` array, so every `$style['variants'] = pz_convert_map(...)` write vanished (verified with a two-line repro: `foreach ($a['x'] ?? [] as &$v) { $v = 1; }` leaves `$a['x']` unchanged). The importer never threw, and every class/page/template still reported the expected `created`/`unchanged`, because the visible symptom is silent — variants stay the artefact's initial empty `[]`, not an error. Fix: `if ( isset( $el['styles'] ) ) { foreach ( $el['styles'] as $sid => &$style ) { ... } unset( $style ); }` — never combine `??` with a by-reference `foreach`.
- `Document::save()` always assigns a fresh random `interactions.items[].value.interaction_id.value` (format `{post_id}-{el_short_id}-{random_hex}`) to every hover/scroll interaction on every call, even when the input `elements` payload is byte-identical to what's already stored — this is Elementor's own behaviour, not something the artefact controls. A raw `_elementor_data` string comparison therefore reports `updated` on every re-import. Fixed by normalizing (stripping) `interaction_id.value` recursively before comparing in `pz_save_document()` (see `pz_strip_volatile()` / `pz_normalized_elementor_data()` in `import.php`); the document is still saved every run regardless, only the changed/unchanged report is corrected.
- `Global_Classes_Repository::put()` only ever wrote the FRONTEND context (`_elementor_used_global_class` equivalent order/items keyed for frontend). The Elementor editor's Style panel and canvas read the PREVIEW context instead (`Global_Classes_Order::make($kit)->set_preview(true)->get_order()`), which starts essentially empty and is never auto-synced from frontend. Symptom: opening the editor on any imported page shows every element's Style panel with only the `local` chip and a "Some classes are missing / A class was removed from your site and is no longer active on this element" warning for every global class, and the canvas renders completely unstyled — even though the published frontend (confirmed via `render.sh`) is pixel-correct. Fixed by calling `Global_Classes_Repository::make(pz_kit())->set_preview(true)->put($items, $gorder)` right after the normal frontend `put()` in `import.php`, mirroring the same `$items`/`$gorder`. Diagnose with `Global_Classes_Order::make($kit)->set_preview(true)->get_order()` — if it's near-empty while the frontend order has all your classes, this is the bug. This preview `put()` overwrites the preview context wholesale, so it also discards any not-yet-published draft change made to a class inside the editor — expected for this pipeline (the artefact is the single source of truth) but worth knowing before running `import.php` while someone is mid-edit.
- `import.php`'s original global-classes order logic only ever APPENDED new ids not already in the stored order (`if (!in_array($c['id'],$gorder,true)) $gorder[]=$c['id']`), so re-declaring an existing class's position in `classes.ts` had no effect at all on a site that had already imported once — the order from the very first import stuck forever, silently defeating the reversed-print-order fix below until the comparison and reordering logic was fixed to treat `classes.json`'s order as authoritative (`array_unique(array_merge($artefact_order, $existing_order))`, artefact first). A class created directly in wp-admin (not by this importer) is kept, not deleted, but demoted below every artefact class in the merged order, so it can never win a same-element property conflict against one the artefact manages.
- Elementor prints global classes to the compiled `global-{post_id}-frontend-{bp}.css` bundle in **reversed** declaration order (`Atomic_Global_Styles::get_document_global_styles()` explicitly does `array_reverse($ordered_class_ids)` before building the css). For two classes with equal specificity applied to the same element, the one declared LATER in `classes.ts` (and thus later in `classes.json`) is printed FIRST and therefore LOSES on any shared property at the same breakpoint/state. Any base class + same-element modifier pair that touches the SAME static (non-`:hover`) property must have the modifier declared BEFORE the base in `classes.ts`, not after — the opposite of what reads naturally. Caught this by noticing the alternating pink/blue service-card tint never showed up even though `svc-pink` was correctly present in the HTML class list and its CSS rule converted fine; `.svc-pink{background-color:...}` was simply overridden by the later-printed `.svc{background-color:...}`. Audited every multi-class combo actually used together in header/footer/home for the same pattern and fixed three: `svc`/`svc-pink`, `lang-item`/`lang-on` (color), `bubble`/`bubble-40`/`bubble-48` (width/height) — all reordered modifier-first. Hover-only modifiers (`card-lift`, `hero-card-l/r`, ...) are unaffected since they set a different state key (`desktop:hover`), not the same one as their base class.
- Elements reference global classes by their readable label (`h1`, `wrap`, ...) in `settings.classes.value` for authoring convenience, but Elementor's `Global_Classes_Relations::extract_class_ids_from_post()` (which drives which classes get bundled into that document's `global-{post_id}-frontend-{bp}.css` file) takes those string values as literal class ids with no label fallback, and `Global_Classes_Repository::get_by_ids()` does a hard-fail lookup with no fallback either. The result: every class converts fine, every page/template saves fine, `verify.php` returns 200 — and the live page renders completely unstyled (no fonts, no flex/grid, no colors), because not one class ever gets linked to the document, so its whole global CSS file is empty (`.hero{...}`, `.h1{...}` etc. simply never printed). Confirmed live: `Global_Classes_Repository::get_by_ids(['g-ccfc59a'])` (the real id) resolves; `get_by_ids(['h1'])` (the label) returns nothing. Fixed by building a `label -> id` map from `classes.json` once and running every element's `settings.classes.value` array through it (`pz_swap_classes()` in `import.php`, called alongside `pz_swap_media()`), leaving already-correct local per-element style ids (`e-<hex>-<hex>`, never a label) untouched. Diagnose this class of bug by requesting `global-<post_id>-frontend-desktop.css` directly (NOT `post-<id>.css`, which only holds page-settings custom css) and checking whether it contains real rules.
- Elementor's own base rule `.e-con{width:var(--width)}` (with `--width:100%` by default) stretches every atomic container (`e-flexbox`, `e-div-block`) to 100% of its parent. For a *column*-direction flex parent or a *grid* parent this is harmless (matches the default stretch behaviour anyway). For a *row*-direction `e-flexbox` parent it is not: an effective `width:100%` makes `flex-basis:auto` resolve to 100%, so every child wraps onto its own line instead of sitting side by side — breaks the header nav, the footer bottom bar, and any other multi-item row whose children don't declare their own width. Confirmed with an isolated headless-Chrome repro using the real downloaded `frontend.min.css` (no live WordPress needed to reproduce or verify). This is a site-wide default, not a per-class bug, so it is fixed once in the child theme (`assets/anim.css`): `.elementor .e-flexbox-base.e-con{--width:auto}` — set the **`--width` custom property**, never the `width` property itself. An earlier version of this rule set `width:auto` directly; at specificity (0,3,0) it beat every global class's own explicit width (e.g. `.elementor .bubble{width:44px}` at (0,2,0)) regardless of which one should win, silently shrinking every sized element (`bubble`/`bubble-40`/`bubble-48`, or any class with its own `width`) down to its unsized default. Overriding `--width` instead leaves the `width` property itself alone, so a class that sets `width` directly still wins on ordinary specificity/order exactly as it always did, and Elementor's own `width:var(--width)` only falls through to our `auto` when nothing more specific sets `width`. Re-run `server/bootstrap.php`'s theme-copy step (or just its step 2) after editing theme files — it always overwrites, no separate flag needed.
- Unpinned wordpress.org zips can serve betas (Polylang did). Only versioned zips.
- `elementor-hf` templates are found by title ("Site header (en)"); renaming a template in wp-admin creates a duplicate on the next import.

## Format
- `nav` is not a valid container tag; use `div` with a `hdr-nav` class. Headings only h1..h6; paragraphs p or span (a span paragraph is the way to make styled inline text or a text link).
- `html-v3` strips every attribute except `a[href]`; `<span class>` becomes `<span>`. Style emphasis via the parent class and the two descendant rules in theme `anim.css` (`.hl-wavy em`, `.em-accent em`).
- A global class renders by label. Labels must match `/^[a-z][a-z0-9_-]*$/i`.
- `transition` easing is dropped; write `transition: transform .25s`.
- `e-grid` base style sets `grid-template-columns:repeat(3,1fr)` and padding 10px, `e-flexbox` base sets padding 10px and row direction: always set `padding` and direction explicitly in a class or local css.
- Container base styles: padding 10px, div-block min-width 30px, grid two equal rows — the builder now zeroes them per element; never rely on the theme for this. Elementor's `.elementor .e-flexbox-base{padding:10px;...}`, `.e-div-block-base{min-width:30px;...}` and `.e-grid-base{...grid-template-rows:repeat(2,1fr);...}` apply to every container regardless of any class or local css we declare, so a `grid()` with only 1 row of real content still rendered an empty second row as tall as the first, every `flex()`/`block()`/`grid()` without an explicit `padding` carried a 10px tint frame, and every `block()` decoration was at least 30px wide even when styled to 2px. Fixed structurally (not per-class) in `dsl.ts`'s `withDefaults()`: `flex()`/`block()`/`grid()` now prepend `padding:0` to their own local css unless a class or their own css already sets `padding`/`padding-*`; `block()` also prepends `min-width:0` unless set; `grid()` also prepends `grid-template-rows:auto` unless set. This runs for every container automatically — no need to remember it per class — and element ids are unaffected since the local style id is derived from the element id, not its css content.
- A block-level widget (e.g. `e-heading`) as a flex-row sibling of a small fixed-size item (an icon) does not reliably share the last line with it just because you set `width:auto` or the `flex` shorthand's default `0 1 auto` on the widget: with `flex-wrap:wrap` on the row, the browser decides which flex line an item goes on using that item's *hypothetical* (unshrunk, single-line) size, not its eventual shrunk size — so a heading whose full text is wider than the row, even though it individually wraps its OWN text fine once given the row's width, still gets the entire line to itself first and pushes the icon to the next line. Flex cannot solve this at all, and an earlier version of this entry recommending `flex:1 1 0%;min-width:0` on the heading plus `align-self:flex-start` on the icon is WRONG and was reverted: a flex item's box is the full row width once its text wraps, so the icon lands at the far right of the block, nowhere near the last word. Use inline flow instead — row `display:block`, heading `display:inline`, icon wrapper `display:inline-block` — which is the only layout that puts the icon immediately after the last word in both the one-line and the wrapped case (then cancel its inline advance, see the negative-margin entry under Environment). Confirmed live by patching the DOM in the browser before committing to a rebuild — much faster than a full pack/push/import cycle per guess. In use in the home `services/h2row` (`h2` + `wink` icon).

- Kit settings are part of the design, not just layout plumbing: `_elementor_page_settings` on the kit controls the `body{}` and `a{}` rules Elementor/Hello print into `post-<kit>.css` (`body_background_background`/`body_background_color`, `body_color`, `body_typography_*`, `link_normal_color`/`link_hover_color`). Without them the theme's own defaults show through — Hello ships `body{color:#333}` at the default `line-height:1.5` with a system font stack, and `link_hover_color` unset falls back to Hello's `rgb(204,51,102)` pink — none of which is visible by looking at `classes.ts` or any recipe, since no element sets its own `color`/`font-family` and inherits from `body` instead. If a whole page reads as "wrong font" or "wrong link color" or "wrong background" with every individual class looking correct, check the kit settings before anything else.
- A class or local css that sets only some padding-family longhands (`padding-top` alone, `padding-inline` alone, etc.) must not be treated as "padding is handled" for the OTHER sides — see `dsl.ts`'s `withDefaults()`, which tracks covered *sides* (top/right/bottom/left), not just "was any padding-shaped property declared". The earlier (wave 2) version used a single regex (`/^padding(-.+)?$/`) that matched any padding-family property and skipped ALL default-zeroing once any one matched, which is why `.ftr-bottom` (declares only `padding-top`) kept Elementor's `.e-flexbox-base{padding:10px}` on its left/right/bottom — invisible in a render slice since it just adds a little space, only caught by reading `getComputedStyle(...).paddingLeft` live.
- An atomic Elementor button widget (`e-button`) ships its own non-transparent `background-color` in its base style. A class meant to be an outline/ghost button (only `border`/`color`, no `background-color`) does not get a transparent background for free — the base style's blue (`rgb(55,94,251)`) shows through wherever the class doesn't explicitly set one. Always set `background-color:transparent` (or `rgba(0,0,0,0)` if the converter ever rejects the `transparent` keyword) on any button class that isn't meant to have a solid fill.
- `font-family` converts ONLY when its value is a `var(--label)` reference to a declared font variable. Every literal value is silently DROPPED — a single family (`font-family:Inter`, `font-family:'Hanken Grotesk'`), a generic (`sans-serif`, `system-ui`) and a whole stack (`system-ui,-apple-system,sans-serif`) all return no `font-family` prop AND an empty `customCss`, so the import does NOT abort and the element simply inherits the kit's body font instead. This is the quietest failure mode in the converter: nothing is reported anywhere, and the only symptom is the wrong typeface live. Every class in `classes.ts` goes through the `BODY`/`DISPLAY` constants (`font-family:var(--font-body)` / `var(--font-display)`) and is therefore safe; the one exception is `photo-credit`, which declares the design's `system-ui,-apple-system,sans-serif` literally and consequently renders in Inter on every page that uses it (Home's two photo credits, For families, and the safety page's). Fixing it needs a `system-ui` font variable in `tokens.ts`, which moves those live pages and so needs its own re-verify. Confirmed with `pz_converter()->convert()` on 2026-09-22. **Never write a literal font family in a class or in an element's local css — always `v("font-display")` / `v("font-body")`.**
- `vertical-align` is not in the 4.2.4 atomic CSS converter's supported property list at all (any value aborts the import as customCss, e.g. `vertical-align:middle`) — same bucket as `pointer-events`. There is no way to express it through a class or local css in this stack. For inline-after-text icon placement, rely on `display:inline-block`'s default baseline alignment instead; it's not pixel-identical to `vertical-align:middle` (sits a few px lower) but reads correctly.
- `.e-flexbox-base.e-con{--width:auto}` (the theme fix for row-direction flex children not filling their row, wave 2) only fixes elements that don't set their own `width`. It does NOT retroactively fix every unsized flex child — a class like `cta-inner` still needs its own explicit `width:100%` if it's the sole child of a row-direction flex parent and doesn't already carry a width-setting class like `wrap`. When auditing, check every single-child `flex()` section for whether its one child is itself a `flex()` (needs a width) versus a `grid()` (stretches by default, fine as-is).

- A container with `tag:"button"` inherits the UA stylesheet's `white-space:nowrap`, and every text child inherits it too, so a long label overflows its row instead of wrapping — and if the parent clips (`overflow:hidden`) the overflow is simply invisible. `white-space` is NOT in the 4.2.4 converter's supported property list at all (same bucket as `pointer-events`, `vertical-align` and `text-wrap`), so it cannot be set from a global class or an element's local css. Caught on the for-families FAQ at 390px: 352px of question text inside a 264px box, with the `+` icon pushed off the card entirely. Two symptoms in sequence, worth telling apart: before `flex:1 1 auto;min-width:0` on the text the item itself overflowed (`scrollWidth` 408 vs `clientWidth` 340); after it the item was the right size but the text still would not wrap, because nowrap was still inherited. Both are needed: the flex pair sizes the box, the theme rule `.elementor .faq-question{white-space:normal}` lets it wrap. Prefer the real `<button>` plus the theme rule over swapping to a `div` — a div is not keyboard-operable.
- Global classes and per-element local styles land in DIFFERENT stylesheets at the SAME specificity: `global-<post>-frontend-<bp>.css` prints `.elementor .<label>{...}` and `local-<post>-frontend-<bp>.css` prints `.elementor .e-<id>-<hex>{...}`, both (0,2,0), with the local sheet enqueued AFTER the global one. So an element's own `css:` map reliably beats any class it carries, which is how a page reuses a shared class and overrides one property (e.g. `h1` for the theme's `text-wrap:balance` plus a local `font-size`) without editing the class and disturbing every other page. The child theme's `anim.css` is enqueued after BOTH, so a theme rule at equal specificity wins over both — which is why a class must NOT declare a property the theme owns (`faq-answer` deliberately declares no `display`, leaving `.faq-answer{display:none}` / `.faq-item.is-open .faq-answer{display:block}` in charge).

## Environment
- `anim.css` (and `faq.js`) are enqueued with `wp_get_theme()->get('Version')` as the cache-busting query string — a STATIC value from the theme's `style.css` header, not a per-deploy hash or timestamp. Editing `anim.css` and re-running the theme-copy step (bootstrap.php step 2, or the inline snippet in `import.php`'s Deploy section) updates the file ON DISK, but a browser (or any CDN) that already cached `anim.css?ver=1.0.0` keeps serving the stale content indefinitely — `?v=<timestamp>` on the PAGE url does not touch the CSS file's own URL/cache key at all. Caught this mid-verification: `getComputedStyle()` kept reporting the pre-fix layout even after confirming the server file was correct, until the page's `<link>` for `anim.css` was reloaded with a manually cache-busted URL. When verifying a theme CSS change, force-bypass the CSS file's own cache (reload its `<link>` with a fresh query string, or bump the theme `Version` header) — do not rely on the page URL's own cache-busting.
- `execute-php` rejects a leading `<?php`. Max execution time is 30 s by default: scripts call `set_time_limit`.
- Do NOT paste the body of `import.php` (14 KB) into `execute-php` on every deploy: run `set_time_limit(600); $r = require WP_CONTENT_DIR . '/novamira-sandbox/artefact/server/import.php'; return $r;` instead — a `return` at file scope is the value of `require`, so the report comes back unchanged, and the same one-liner works for `bootstrap.php`/`verify.php`/`snapshot.php`. It cuts a deploy from ~15 KB of prompt to three lines, which matters when a fidelity pass needs five or six round trips. Two caveats: `require` a script only ONCE per request (a second `require` in the same call fatals with `Cannot redeclare pz_fill_styles()`), so run the idempotency re-import as its own `execute-php` call; and the unzip step can be inlined ahead of it (the five lines of `unpack.php`) so unpack + import are a single round trip.
- Elementor CSS is cached in uploads/elementor/css; `files_manager->clear_cache()` after imports, and render with a `?v=` query.
- The built-in browser pane is narrow (1024px); the editor panel scrolls horizontally. Use `read_page` refs for clicks, not coordinates.
- Editor Publish is disabled when nothing changed; a round-trip test needs a real edit.
- Theme CSS exceptions (the only hand CSS): keyframes behind `anim-*` classes, the `.hl-wavy em`/`.em-accent em` rules, the `--width:auto` flex-row fix, and `text-wrap:balance` on the heading classes (`h1`, `h2`, `h2-light`, `h2-sm`, `h2-cta`) because the design relies on balanced heading breaks and the 4.2.4 converter has no `text-wrap`. Bump the theme `Version` in style.css whenever `anim.css` changes: it is the cache-buster for the enqueued stylesheet.
- Intrinsic sizing keywords (`width:fit-content`, `min-width:max-content`, `max-width:fit-content`) are NOT convertible in 4.2.4 — they fall through to `customCss`, which Free drops, so the importer aborts. `calc(...)` and `clamp(...)` DO convert, as custom sizes.
- An inline icon after a heading (the services wink) can be pushed onto a line of its own whenever the heading fills the row, because the whitespace between the two elements is a wrap opportunity and there is no `white-space:nowrap` in the V4 schema. Cancel the icon's inline advance with a negative right margin equal to its width plus its left margin (`margin-left:12px;margin-right:-52px` for a 40px icon): line breaking then treats it as zero-width, so it always stays with the last word and overflows harmlessly into the gap that follows.
- A flex child with `flex:0 0 auto` and a `max-width` cannot shrink, so it overflows the viewport on mobile; use `flex:0 1 auto` so the same element collapses to the available width once it wraps onto its own line.

- The 4.2.4 converter rejects several values whose siblings convert fine, so guess-by-analogy is unsafe — ask the site (`require .../lib.php; return pz_converter()->convert('<css>');`, many declarations in one call) before writing any of them. Confirmed rejections and their working substitutes: `text-align:left` fails while `start`/`end`/`center`/`justify` pass (use `start`); `align-items:baseline` fails while `flex-start`/`center`/`flex-end`/`start`/`end`/`stretch` pass; `justify-self` and `place-self` fail at any value (centre a grid item with `margin-left:auto;margin-right:auto`); `object-position` fails in keyword form (`right bottom`, `center`) but passes as percentages (`100% 100%`); `background-size`/`background-position` fail ON THEIR OWN but pass when declared alongside a `background-image` in the same block (they merge into one `background` prop), which is why the existing home photo blocks convert and an isolated `background-size:cover` would not. Convertible despite being absent from css-cheatsheet.md: `cursor`, `min-height`, `max-width:<%>`, three-value `padding` shorthands, `width:min(...)`, `grid-column:span N`, `font-style`.
- Chrome headless clamps `--window-size` to a floor of about 500px, so a `--window-size=390,9000` run silently lays the page out at 500px and any mobile measurement taken from it is wrong (it reported `documentElement.clientWidth` 500 while claiming to be 390). To measure a real narrow viewport without the browser pane, load the page inside a fixed-width same-origin iframe in a harness page and run the probe against `iframe.contentDocument` — the iframe's own width is the inner document's layout viewport. Serving a `curl`ed copy of a live WordPress page from a local static server works for this because WordPress emits absolute URLs for every stylesheet, script and image; only nav links are relative, and those are not needed for measurement.
- A load-triggered V4 interaction (e.g. `effect:"scale"` on the `vetted` badge) is frequently caught MID-ANIMATION by a headless capture, because `--virtual-time-budget` fast-forwards timers unevenly: the same element measured 71x23, 50x?, 19x7 and 0x0 across runs at different widths. Do not chase it as a layout bug — re-read it in the real browser (`transform:none`, full size) before spending a deploy cycle on it. The same caveat already applies to `.dash` under `anim-wiggle`.

## Anchors and in-page navigation
- **A V4 atomic element DOES render an `id`** — through the `_cssid` setting, not the class list.
  Every element type has it (`Flexbox`, `Div_Block`, `Grid` and the widgets all read
  `$settings['_cssid']` in `add_render_attributes()` and emit `id="…"`), and the editor exposes it
  as the "ID" text control in the Settings tab. Verified live on 4.2.4 by rendering each type with
  `create_element_instance()->print_element()`. Earlier pages recorded "a V4 atomic element renders
  no `id`, so there is nothing to anchor to" as a named deviation on four pages' hero buttons — that
  was wrong, and those four inert buttons can be made to work whenever someone re-verifies those
  pages. The builder exposes it as `cssId` on any element (`dsl.ts`).
- `scroll-margin-top` converts; the logical `scroll-margin-block-start` does NOT (customCss, aborts).
- Elementor's `frontend.min.css` sets `html{scroll-behavior:smooth}` site-wide, so every in-page
  jump on a WordPress page is animated where the design's own page jumps instantly. **Headless
  Chrome never runs that animation under `--virtual-time-budget`**: `window.scrollTo()`,
  `scrollIntoView()`, setting `location.hash` and clicking an anchor all leave `scrollY` at 0, on
  every page of the site, which reads exactly like "the page cannot scroll" or "the anchors are
  broken". It cost a long bisect here. To measure a jump, inject `<style>html{scroll-behavior:auto}
  </style>` into the copy under test and nothing else; the design page (which has no such rule)
  scrolls normally and is the control that tells the two apart.
- Measure a scroll/anchor jump on a TOP-LEVEL document, never inside the harness iframe: an iframe
  at a fixed height reports the right `scrollHeight` but will not scroll the inner document, so
  every jump reads as 0. Serve a `curl`ed copy of the live page and append the probe before
  `</body>`, then `--dump-dom` it.

## Size properties
- The size properties (`min-width`, `max-width`, `min-height`, `max-height`) convert only a length
  or a percentage. Every CSS-wide keyword — `none`, `initial`, `unset`, `inherit`, `auto` — lands in
  customCss and aborts the import, so a responsive breakpoint cannot *reset* a cap the way a design's
  media query does (`max-width:none`). Use a real value with the same effect: `max-width:100%` for a
  stacked flex item, and a very large length (`max-height:100000px`) for "no cap". `width:auto` and
  `height:auto` are fine — they are not in this set. `css.ts` lints this now.

## Blog (the non-Elementor templates)
- **An `<a>` inside an `<a>` silently destroys a card.** The index and "Keep reading" cards are one
  big link; the photo-credit overlay inside them must be plain text, never the linked Unsplash
  attribution. The HTML parser closes the card link at the nested `<a>` and re-parents everything
  after it, so the card's picture and body become loose grid items and the layout collapses — with
  the page HTML still looking perfectly correct in `curl`. Caught only by `getComputedStyle`
  reporting `.post .pic` as MISSING. `poppynz_blog_figure()` takes a `$linked` flag for this.
- **`update_option('permalink_structure', ...)` does not tell `$wp_rewrite`.** The object keeps the
  previous structure for the rest of the request, so a `flush_rewrite_rules()` in the same request
  writes the OLD rules. Use `$wp_rewrite->set_permalink_structure()`, then flush. Symptom: every
  post 404s until some later, unrelated flush.
- **A bare `/%postname%/` permastruct lets a page shadow a post of the same slug.** WordPress uses
  verbose page rules and matches pages first, so the `daycare-matching` article was unreachable
  behind the Daycare matching page. The blog permastruct is `/blog/%postname%/`.
- **A draft will not keep the date you give it.** WordPress leaves `post_date_gmt` at
  `0000-00-00 00:00:00` on a draft and then refreshes `post_date` to "now" on every save. Pass an
  explicit `post_date_gmt` and `edit_date => true` or the import is never idempotent.
- **`get_permalink()` on a draft returns `?p=<id>`.** Use `get_sample_permalink()` (wp-admin/
  includes/post.php) when you need the URL a draft will have once published.
- One stylesheet serving two designs inherits both designs' class names. `.tag` is the index's
  filter pill in one and a bare icon+label inside an article's levels card in the other; the pill
  has to be scoped (`.tag-row .tag`) or it draws a border around the other one.
- `require`-ing two server scripts in one `execute-php` call shares variable scope: `unpack.php`
  reassigns `$dir`, which broke a following `require $dir . 'server/bootstrap.php'`. One script per
  request, as SKILL.md says.
